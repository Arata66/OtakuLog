# 可复现部署实施与验收

日期：2026-10-08。承接第一阶段 B，用户已授权继续实施。

## 问题与方案

- Compose 没有覆盖 JDBC 地址，应用会连接容器自身的 localhost；改为服务名 `mysql`，数据库名统一为 `otakulog`。
- 数据库容器启动不等于可连接；用真实 SQL 健康检查，应用等待数据库健康后启动。
- MySQL 仅供应用容器访问，移除宿主 3306 映射，避免与本地数据库冲突；应用端口允许通过 `APP_PORT` 调整。
- 传入管理员环境变量，说明数据卷保留、密码初始化语义与升级步骤。
- 检查发现 V1 快照含有 V2、V3 重复添加的列。先写真实 MySQL 空库测试复现，再增加 V0 初始结构：空库先创建 V2 之前的表，V1 的 IF NOT EXISTS 自动跳过；已有库的历史脚本和校验和保持原样。
- 真实启动还暴露 VARCHAR 状态列与 Hibernate 原生 ENUM 映射不一致。新增 V8 Java 迁移对齐类型：已有相同 ENUM 不改表；转换前拒绝未知值，防止非严格 SQL 模式静默转换数据。

## 执行步骤

1. 添加显式启用的 MySQL 集成测试；每次随机创建独立测试库，只清理该次创建的库。
2. 验证空库初始化、应用两次启动后的数据保留；验证 V5 数据升级后番剧、标签、分组与逐集日期保留。
3. 增加 V0 初始化脚本与 V8 类型对齐，保持 V1—V7 和 V6.1 不变，重复运行测试。
4. 修正 Compose，验证配置解析；Docker 可运行时使用独立项目和数据卷验证容器启动、重启与持久化。
5. 执行 Java 编译、全套测试、JS 行为测试及空白检查，同步 README 和项目记忆，提交并推送。
6. 收尾启动当前开发版本，检查现有本地数据库与登录页面。

## 验证边界

禁止对现有 `otaku_log` 库做初始化、升级实验或删除操作。隔离测试库前缀为 `otakulog_verify_`；容器验证采用独立项目名，不能删除既有数据卷。

本地 MySQL 测试能证明迁移及应用兼容性，不能证明容器健康检查和容器网络。Docker 未运行时明确记录未验证项。

## 结果

- 修复前：两个 MySQL 用例都在 V2 报 `Duplicate column name 'created_at'`，复现空库部署失败。
- 增加 V0 后：进一步复现状态列 VARCHAR 与 Hibernate ENUM 不一致；V8 修复后，空库应用启动及 JPA 读写、重启保留数据、V5 带数据升级、V1 基线兼容均通过。
- 未知状态用例验证迁移拒绝执行且原值和 VARCHAR 类型保留，避免静默转换数据。
- Java 17 干净编译通过；启用 MySQL 后全部 75 个 Java 测试通过，无失败、错误或跳过；16 个 Node 行为测试、4 个 JS 语法检查、空白检查通过；可执行 JAR 打包通过。
- Docker Compose 5.1.3 实际解析通过，确认 JDBC、数据库名、管理员变量、SQL 健康检查和 `service_healthy` 依赖；MySQL 无宿主端口映射。
- 本机有 Docker CLI 和 Compose 文件，但 Docker Desktop 启动日志报告缺失 `SOFTWARE\\Docker Inc.\\Docker Desktop` 注册信息，Docker 引擎管道不存在。容器构建、延迟就绪和容器卷重启验证尚未执行，B 不标记全部验收完成。不自动安装或重装系统组件。
- 当前分支已重新打包并后台启动 `http://localhost:8080`；登录页 200、匿名 API 401、真实登录后 API 200，现有 11 部番剧可查询。自用库 V8 执行成功，状态列原本已是目标 ENUM，无需改表。

## 后续容器验收

在可运行 Docker 的环境，用独立项目名、未使用的端口和全新卷执行；如已有同名容器，先在临时覆盖文件中更换 `container_name`，不能停止其他实例。

1. 启动 MySQL，确认健康检查从初始化转为 healthy，再启动应用并确认日志完成 Flyway 与 JPA 校验。
2. 登录后添加一条验收番剧，重启应用、再停止并启动整个项目，确认数据保留。
3. 确认不会在 MySQL 不健康时启动应用；模拟数据库延迟恢复后再次启动并检查可连接。
4. 清理时仅删除该次验收创建的项目和卷，不把日常服务的 `down -v` 当成停止步骤。

数据库迁移的生产配置仍为 `validate`；没有为绕过失败而改用自动建表。

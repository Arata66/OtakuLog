# 逐集记录查看与日期补录实施计划

用户已授权自行决定后续步骤并继续实施；沿用可靠自用工作区与分支，单代理执行。

目标：在作品详情内核对逐集日期、补录历史，并保持进度、状态、统计和备份语义一致。

方案：复用详情弹窗，避免增加独立页面；逐行保存，避免批量误确认旧估算。新增独立记录服务与控制器，写入仍统一委托 WatchProgressService，不改表结构。

## 行为约定

- 列出进度内各集及已有的进度外记录，区分缺记录、未知日期和 LEGACY 历史来源不明。
- 每页 20 条，接口允许 1–50 条；分页不按进度创建大数组。
- 日期不预填今天。保存日期变更或明确核对 LEGACY 后来源为 MANUAL；清空日期保留 NULL。未变的明确来源记录保持原来源与审计时间。
- 不修改进度、状态、作品观看起止日期；禁止新增进度外记录；拒绝未来日期与 MySQL 日期范围之外的日期。
- 请求必须携带原记录快照（集号、是否存在、记录 ID、日期、来源、更新时间）。锁定番剧后比较，过期返回 409；前端提示重载，不自动覆盖。
- LEGACY 核对和清空已知日期需明确确认。关闭或切换详情后，旧请求不得更新新弹窗。
- 成功后刷新记录与热力图；年报下次打开重新获取。完整备份继续保留日期、来源与审计信息。

## 接口

`GET /api/anime/{id}/episodes?page=0&size=20` 返回 animeId、currentEpisode、page、size、totalRows、entries。entry 包含 episodeNumber、recorded、recordId、watchedDate、source、updatedAt。

`PUT /api/anime/{id}/episodes/{episodeNumber}` 请求 `{watchedDate: "2026-01-02" 或 null, expected: 原 entry}`。成功返回 200；非法参数 400，缺作品 404，快照冲突 409；需登录与 CSRF。

## 验证结果

- Java 17 离线干净编译、测试及打包通过：165 个 Java 用例，无失败、错误或跳过，包含 20 个逐集记录用例与 8 个真实 MySQL 用例。
- 39 个 Node 行为用例、5 个 JS 语法检查通过；保存一行时保留其他草稿，未修改旧值不会盖住最新查询值。
- 并发核对同一 LEGACY 快照只有一次成功；核对后年报明确观看量变化、清空日期与完整备份恢复均在随机 MySQL 库验证。
- H2 的古日期 JDBC 转换在 Asia/Shanghai 下与 MySQL 不同。最小 JDBC 实验确认问题位于 H2，`1000-01-01` 的准确存储往返改由真实 MySQL 用例验收，不给业务添加日期偏移补偿。
- 真实 HTTP 登录、逐集只读查询、年报、完整导出、只读恢复预览和匿名拒绝通过；浏览器登录与详情来源展示已检查。
- 启动后首轮只读验收为 11 部作品、62 条 LEGACY 记录，日期校验值 120172387655；年报完成 4 部、明确观看量 0、历史参考 62、进度缺记录 12。随后网页核对产生一条 MANUAL 来源，原日期未变；保留与否需用户确认，不应自动回滚用户可能已确认的操作。
- 未进行移动端浏览器与完整保存流程端到端验收；确认取消、草稿、冲突、关闭后的响应由 Node 行为测试覆盖。Docker 容器运行仍沿用 B 的待办。

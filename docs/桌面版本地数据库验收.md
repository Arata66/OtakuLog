# 桌面版本地数据库验收

验收日期：2026-10-16—17。范围为实施计划第1阶段的 H2 文件库、原业务写入与完整备份兼容。全部样例为虚构资料，使用随机临时目录和本次成功创建的 MySQL 隔离库，不连接自用资料做写入实验。

## 文件库与版本保护

桌面只执行 `db/desktop` 迁移，JPA 保持 `validate`；原 MySQL 历史迁移不变。`DesktopDatabaseTest` 共6例，覆盖空库、中文空格路径、重开持久化、AI 开发配置隔离、路径拒绝、结构损坏与未来版本拒启。

未来版本测试真实完成 V1 写入、V2 增列迁移，再用只有 V1 的当前程序打开：启动在 Flyway 校验阶段失败，原作品、额外列和成功迁移历史仍保留。原行为已复现为只警告后继续启动；desktop 专属 customizer 清空 Flyway 默认的未来版本忽略规则后通过回归。此项是拒绝降级保护，不表示升级前自动备份已交付。

## 写入与并发

`DesktopWriteConsistencyTest` 共10例，使用真实文件库、Flyway 和服务事务：

- 两窗口同时进集均累计成功，再顺序退回计划并同步删除逐集记录。
- 未知日期保持 NULL 与原来源，热力图不猜日期；同一逐集快照竞争只接受一次，保留微秒审计。
- 16000 字中文感想在重复提交与重启后原样保留；同 UUID 不同内容冲突，同记忆版本并发编辑仅一次成功，旧版本不能删除。
- 最早支持的观影日期 `1000-01-01` 原样保存，SQL 原值、备份恢复与重启一致；同一更新入口拒绝 `0999-12-31` 且完整备份不变，非零微秒审计不丢失。
- 推荐反馈同键并发防重，撤销后重启不复活，不生成观看日期。
- 同一收藏预览同时确认只执行一次，重启后仍防重；外部原评论保留，逐集日期为未知。
- 回环假模型等待期间同键不重发，空备份恢复可完成；额度不退还，实际用量保留。
- 恢复等待 quota 或 import_lock 时不提前锁下游资源，继续遵循 quota → import_lock → 作品。
- 真实唯一键、外键及删除级联生效。

发现的 H2 兼容差异是 SERIALIZABLE 事务在等待固定导入锁前建立旧快照，拿锁后看不到前一事务刚提交的防重结果，可能触发外部收藏唯一键冲突。测试先持有固定锁并确认两个请求均等待，稳定复现旧行为；只将 desktop 收藏导入改为 READ_COMMITTED。固定导入锁、作品锁、整批事务和防重校验保持，网站默认 SERIALIZABLE 另有真实 JDBC 连接断言。

日期边界还发现 Hibernate 6.3 默认经 `java.sql.Date` 绑定和读取 H2 DATE，历史历法与本机时区转换会偏移日期。直接 JDBC 对照确认 H2 的 `setObject/getObject(LocalDate.class)` 可准确往返；因此仅 desktop 为 `LocalDate` 注册 JDBC 4.2 绑定与读取，其他 DATE 类型回退原实现。未改实体、依赖或全局时区，上海时区与 UTC 的下界用例分别通过。

## 完整备份对照

`DesktopBackupRoundTripTest` 共8例，其中真实 MySQL→H2 和双库文本比较两例需要显式启用 MySQL 测试，其余六个文件库用例始终运行。文本比较中的 H2 部分也随该双库用例一起执行，不能计入未启用 MySQL 的 Windows 运行结果。

MySQL 来源先制造作品、标签和分组 ID 空洞，再填充完整 v6 十三集合：作品、标签、分组、关联、逐集记录、记忆、观点、调用历史、外部收藏、导入批次、推荐条件、反馈及观点推荐关联。导出后恢复到空 H2，重新导出、重复恢复并重启核对。H2→H2 也执行相同全量对照。

对照仅规范化导出时间、集合顺序和具体引用字段，保留全部业务字段、稳定 UUID、原文、模型原建议与用户改写、版本、微秒审计、历史 owner 及停用/撤销历史；不能只比较作品数量或对整个 JSON 做字符串替换。

另覆盖旧数组、v1—v5；八类同 UUID 内容冲突夹带新作品；损坏 JSON、缺集合、缺审计和非法枚举。预览和实际恢复都必须拒绝，原十三集合保持不变。恢复 RUNNING 保留可备份历史，内部 `historyOnly` 标记不进入文件或内容比较；同键不外发，原有当天额度不下降，重复恢复与重启不重发。恢复测试的回环服务核对零 HTTP 外发。

## 名称、标签与排序差异

双库比较使用页面实际采用的分页服务，真实新增、搜索和绑定标签。受测 MySQL 的 `anime.name`、`tag.name` 列均为 `utf8mb4_0900_ai_ci`；其他部署按其实际列规则判断，不能把该结果推广为所有 MySQL 的默认规则。

| 用户行为 | H2 REGULAR 普通 VARCHAR | 本次受测 MySQL 列 |
|---|---|---|
| 再添加完全相同的 `CaseAlpha` | 拒绝同名 | 拒绝同名 |
| 再添加仅大小写不同的 `casealpha` | 作为不同名称保留 | 拒绝同名 |
| 搜索 `case` / `CASE` | 分别命中2个 / 0个 | 均命中3个 |
| 名称升序 | CaseAlpha、CaseGamma、casealpha、casebeta | CaseAlpha、casebeta、CaseGamma |
| 为作品绑定 `CaseTag` / `casetag` | 保留两个标签，分别有2/1次引用 | 复用同一标签，共3次引用 |

桌面沿用 H2 的大小写比较与排序，未改动全库 collation；原名称和标签原文保留。UUID 集合按稳定编号识别，作品恢复还使用精确名称或 Bangumi ID，分组和标签也涉及名称匹配。因此已验证的 MySQL→空 H2、H2→H2 往返不等于 H2→MySQL 的大小写变体合并已验收；本阶段不承诺跨数据库排序完全相同，也未用 ASCII 样例推断全部重音及语言排序。

## 执行方法与边界

本地最终全量构建为447项 Java 测试，零失败、零错误、零跳过；随后新增的双库文本比较用例单独通过，默认 Java 编译和桌面 lint/类型检查通过。两部分合计448项本地用例，远程 CI 仍按最终提交重新执行全套，不能把定向新增用例说成已参加先前全量构建。

在 Java 17 环境运行；启用 MySQL 前按本机配置设置 DB_USER、DB_PASS，只允许测试创建的随机库参与：

```powershell
$env:OTAKULOG_MYSQL_TEST='true'
mvn -q -Pdesktop '-Dtest=DesktopDatabaseTest,DesktopWriteConsistencyTest,DesktopBackupRoundTripTest' test
mvn -q -Pdesktop clean verify
mvn -q -DskipTests compile
git diff --check
```

Windows CI 没有 MySQL 服务，明确跳过真实 MySQL 用例；原 Ubuntu CI 提供隔离 MySQL 服务执行跨库与原网站回归，不能把 Windows 跳过算作已执行。

本轮恢复与写入交错验证针对既有作品的锁顺序；恢复期间普通新增同身份作品的既有竞争问题仍为可靠性待办，不能据此宣称全部创建入口已有统一身份保护。

本阶段不证明自动备份、统一导出快照屏障、升级失败恢复、桌面原生文件对话框或干净系统候选包已经完成。应用完整备份语义见[备份与恢复](备份与恢复.md)，后续仍按[实施计划](superpowers/plans/2026-10-15-Windows桌面版.md)推进。
